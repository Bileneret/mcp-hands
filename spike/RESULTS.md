# Этап 0. Результаты замеров: UIA-зонд

Дата: 17.10.2026. Стенд: Windows 11 (10.0.26120), Python 3.12.0, comtypes + UIAutomationCore,
GTX 1650 4 ГБ, монитор 1920×1020 @ DPI 96 (100%), режим процесса — `PER_MONITOR_AWARE_V2`.

Цели: Блокнот (WinUI/XAML), Opera (Chromium), Antigravity (Electron, форк VS Code).
Telegram на стенде не установлен — заменён на Electron-приложение, то есть на более
сложный случай из тех, что перечислены в DESIGN.md §4.2.

Воспроизведение:

```
python -u spike/measure_uia.py --exe Notepad.exe --exe opera.exe --exe Antigravity.exe \
       --warmup 1 --runs 2 --jump auto --modes cached,perparent,propcost,descendants
python -u spike/measure_uia.py --only-hang          # зависшее окно, таймауты
```

Сырые данные: `results_uia_jump.json` (обходы), `results_uia.json` (без прыжка),
`results_hang.json` (таймауты).

---

## 1. Главная находка: семантика кэш-реквеста

Документация читается так, будто область кэш-реквеста отсчитывается от корня поиска.
Фактически она отсчитывается **от каждого элемента результата**. Отсюда:

| Связка | Что получается |
|---|---|
| `search=Children` + `cache=Children` | контейнеры без свойств: чтение `Cached*` падает с `E_INVALIDARG` (0x80070057), шаг вглубь через `FindAllBuildCache` — `E_FAIL` |
| `search=Children` + `cache=Subtree` | элементы со свойствами, потомки уже в кэше: спуск через `GetCachedChildren` не делает межпроцессных вызовов (0.01 мс на уровень) |

Рабочая схема поэтому такая: **один `FindAllBuildCache(Children, cache=Subtree)` + клиентский
спуск по `GetCachedChildren`**, а ограничение глубины применяется на нашей стороне.
`GetCachedChildren` возвращает NULL у листьев — в `uia_common.cached_children` это
превращается в пустой список, иначе comtypes падает на `ValueError`.

## 2. Цена свойств: кэш против `Current*`

Один и тот же набор элементов, профиль `action` — 26 свойств на элемент
(режим `propcost`, чтобы сравнение не зависело от формы дерева):

| Цель | Элементов | Из кэша | Через `Current*` | Выигрыш |
|---|---|---|---|---|
| Блокнот | 29 | 1.60 мс | 48.6 мс | 30× |
| Opera (Chromium) | 10 | 0.66 мс | 18.5 мс | 28× |
| Antigravity (Electron) | 27 | 1.50 мс | 70.0 мс | 46× |

На элемент: 0.055 мс из кэша против 1.7–2.6 мс через `Current*`, то есть **≈70 мкс на одно
свойство** межпроцессно. Именно это оправдывает правило «все свойства за один переход»
из DESIGN.md §4.2: чтение сырого дерева Chromium (383 элемента) без кэша стоит ~0.7–1 с
на один кадр.

## 3. Стратегии обхода (глубина 3, после прогрева)

| Цель | `cached` (1 переход + спуск) | `perparent` (переход на родителя) | Полное поддерево (`descendants`) |
|---|---|---|---|
| Блокнот | 29 эл. / **53.5 мс** | 29 эл. / 116.9 мс | 53 эл. / 142.6 мс |
| Opera | 10 эл. / **46.7 мс** | 10 эл. / 158.8 мс | 383 эл. / 598 мс |
| Antigravity | 27 эл. / **97.7 мс** | 27 эл. / 306.6 мс | 764 эл. / 1052 мс |

`cached` выигрывает у `perparent` в 2.2–3.4 раза при том же результате — на Chromium
один межпроцессный переход стоит ~45 мс. Полный обход дерева слишком дорог для
внутреннего цикла (у Electron — больше секунды), поэтому рабочий режим «глаз» должен быть
поисковым (адресный запрос по предикату), а не «обойти всё и отфильтровать».

## 4. Корень контента: без прыжка до страницы не дойти

Обход от верхнего окна на глубину ≤3 до содержимого Chromium/Electron **не доходит**:
у Opera до страницы 8+ уровней хрома браузера (`RootView → NonClientView → … →
BrowserClientViewGx`). Найден рабочий порядок:

1. видимый дочерний HWND класса `Chrome_RenderWidgetHostHWND` (чистый Win32, **0.17 мс**,
   ни одного вызова UIA) — есть у Chromium;
2. иначе `FindFirst(Descendants, ControlType=Document)` — **50–95 мс**, один переход;
3. иначе само окно.

| Цель | Корень | Элементов (глубина 3–4) |
|---|---|---|
| Opera | `Chrome_RenderWidgetHostHWND` (0.17 мс) | 13 против 4 без прыжка |
| Antigravity | `Document` (85–95 мс) | 27 против 6 без прыжка |
| Блокнот | прыжок не нужен: `Document` — лист | 34 от окна |

Оговорка по Блокноту: его `Document` — текстовое поле-лист (текст отдаётся `TextPattern`,
детей нет). Поэтому в `--jump auto` есть откат: если у выбранного корня ноль детей,
обход повторяется от окна.

## 5. Зависшее окно: таймауты

Фикстура `hang_window.py`: окно перестаёт разбирать сообщения через 0.4 с после старта.

| Защита | Результат |
|---|---|
| без защиты | вызов **не вернулся**: убит на 45 с (кап замера) |
| процесс-зонд с бюджетом 500 мс | убит на **523 мс** (+23 мс накладных) |
| `ConnectionTimeout` 200 мс | прерван на **217 мс**, COMError `0x800705B4` |
| `ConnectionTimeout` 500 мс | прерван на **517 мс**, COMError `0x800705B4` |
| `ConnectionTimeout` 1000 мс | прерван на **1028 мс**, COMError `0x800705B4` |

Что из этого следует:

- оценка DESIGN.md «COM-поток виснет на 5–15 с» была **оптимистичной**: без таймаута вызов
  не возвращается вообще;
- `IUIAutomation2.ConnectionTimeout` работает точно (±3%) и даёт **внутреннюю** защиту —
  исключение вместо зависания, без перезапуска процесса-зонда;
- таймаут не ломает здоровые длинные запросы: полный обход Chromium (383 элемента,
  1.05 с) с `ConnectionTimeout=500` прошёл идентично прогону по умолчанию;
- заводские значения: `ConnectionTimeout` = 2000 мс, `TransactionTimeout` = 20000 мс;
- процесс-зонд с kill остаётся второй линией защиты (от зависаний, которые таймаут
  не покрывает) — 523 мс против 45+ с у наивного варианта.

## 6. Доступность в Chromium/Electron включается лениво

Первый контакт с Antigravity дал 13 потомков (только хром окна), после серии UIA-запросов
то же дерево — 764–778 элементов. У Opera дерево было готово сразу (430–538).
Практический вывод: перед работой с Chromium/Electron нужен прогрев с повтором, а первый
пустой ответ нельзя трактовать как «приложение без доступности» и уходить в пиксельный
фоллбэк. Точное время прогрева не измерялось (потребовался бы перезапуск приложения) —
задача перенесена в отчёт как открытый вопрос.

## 7. Что меняется в DESIGN.md

1. §4.2 «глубина ≤ 3» уточняется: **обязательный прыжок к корню контента**, затем
   ≤3 уровня от него. Без прыжка страница Chromium/Electron недостижима.
2. §4.2 защита от зависаний: **`ConnectionTimeout = 500 мс` как основная** (в процессе),
   процесс-зонд с kill — резервная.
3. §4.2 добавляется прогрев/повтор для Chromium/Electron.
4. Модель работы «глаз»: адресные запросы по предикату вместо полного обхода дерева
   (полный обход Chromium/Electron — 0.6–1.1 с).

## 8. Открытые вопросы

- Время прогрева доступности Chromium/Electron (нужен перезапуск приложения).
- Кэш-реквест с `TreeFilter` по типам элементов: срежет ли он стоимость полного обхода.
- Дешёвый ли адресный `FindFirstBuildCache` по имени — цена поиска конкретной кнопки
  против полного обхода (следующий замер, нужен для планировщика).
- Поведение на русской локали подтверждено (интерфейс Блокнота и Opera — кириллица).
